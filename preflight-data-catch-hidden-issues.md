**Why the bioinformatics / research-data domain context still matters for interpreting the talk:**

- Bioinformatics and research data more broadly are a *canonical worst-case* for data quality: multi-vendor instruments, metadata curated by humans across institutions over decades, file formats that evolved organically (FASTA, FASTQ, BAM, VCF — each with their own dialect of "almost-standard"), and downstream analyses that fail weeks later because an upstream column drifted silently.

## Notes

- **First slide / opening hook:** *"Most broken datasets don't look broken."*
  - **The talk's central premise in seven words.** Captures exactly why the "preflight" framing is necessary: if broken data were obvious, you wouldn't need a preflight discipline — you'd see the problem at first glance and triage it. The dangerous failures are the *plausible-looking* ones: data that loads cleanly, parses without warnings, runs through every dashboard you have, and is wrong in a way that only becomes apparent downstream (in a published paper, a regulatory filing, a model prediction, a cascade of dependent analyses).
  - **The failure-mode taxonomy this implies:**
    - **Wrong-units that share a type** — kilograms vs. grams, Celsius vs. Fahrenheit, ISO dates vs. US dates. All numeric / string-of-the-expected-shape; only domain knowledge says which is correct.
    - **Wrong-column assignments** — values are valid for the column they ended up in but were intended for a different column (latitude/longitude swapped, first-name/last-name reversed). Type checks pass; semantics are inverted.
    - **Stale-but-fresh-looking timestamps** — a pipeline that's been silently broken for a month but the `updated_at` field gets bumped on every empty-run, so freshness monitors say "data is hours old" when actually no new content has flowed in for weeks.
    - **Encoding subtleties** — a UTF-8 string that *looks* right in your terminal but has a zero-width-space, a smart-quote, or a homoglyph that breaks joins. The data displays correctly; equality comparisons fail mysteriously.
    - **Schema drift below the type level** — a field that *was* "two-letter state code" silently expanding to include three-letter Canadian province codes; a field that *was* free-text becoming a controlled vocabulary; a taxonomy ID that got renumbered upstream. The shape is unchanged; the *semantics* shifted.
    - **Plausible-but-impossible combinations** — a specimen collected in 1850 in a country that was established in 1947; a temperature reading 800°C in a habitat where the organism is alive; a species name that hasn't been valid since 1972 paired with a recent collection date. Each field on its own is plausible; the *combination* is impossible.
  - **Connection to the earlier Constance Martineau talk** (the SWE-vs-DE one — see [notes](swe-best-practices-fail-data-engineering.md)): Constance's empirical kill-shot was *"your tests pass, your CI/CD is green, and then upstream drops a column."* Jennifer's opening is the *generalization* of that observation past schema-drop into the much wider universe of subtle-but-wrong data. **Constance documented one specific failure mode; Jennifer is framing the entire category.** Both talks are responses to the same underlying truth: validation that only checks *form* (does this parse, does this satisfy the schema) catches a small fraction of real failures, because most real failures are at the *meaning* layer.
  - **Why "preflight" is the right metaphor.** Aviation preflight inspections exist because the cost of discovering a problem mid-flight is catastrophically higher than the cost of discovering it on the ground. Same shape applies to data handoff: a problem caught before a dataset moves to the analyst / the model / the publication / the next team is dramatically cheaper to fix than one discovered three steps downstream. **The talk is presumably going to walk through the equivalent of a preflight checklist for data** — concrete inspections you run *before* handing data off, where each inspection cheap and the consequence-of-skipping each one is non-trivial.
  - **Predicted talk structure** (listening aid; await actual content):
    - The categories of "doesn't look broken but is" failures (likely with bioinformatics / museum examples)
    - The preflight checklist itself — what to inspect, with what tools
    - Where these checks fit in the pipeline (CI? handoff gate? upstream alerting?)
    - Tooling — likely some combination of Great Expectations, Pandera, custom validators, dbt-tests, or her own FAIRy/airy project
    - Organizational angle — who owns the preflight, who gets blocked by failures, how to socialize the practice
- **Worked example — fishermen → analysts, mussel data.** Speaker grounds the abstract "looks right but isn't" framing in a concrete scenario: **fishermen collecting mussel data that gets handed to analysts downstream.** The data looks fine when the analyst opens the file; the analysis silently uses bad assumptions because the *collection process* introduced errors that no schema can catch.
  - **Why this is a perfect canonical example for the talk's thesis:**
    - **Two-party handoff with no shared context.** The fisherman knows the boat, the weather, the gear they used, and the conditions of collection. The analyst opens a CSV. *None of that context is in the file.* Anything not encoded in the columns is invisible to the consumer — even when it materially affected the data quality.
    - **Field-collected scientific data is the hardest case.** Wet hands, rocking boat, ad-hoc forms, end-of-day fatigue, fishermen who weren't hired to be data clerks. The *data-collection environment* is hostile to data quality in ways the data itself doesn't reveal.
    - **Mussel data specifically** has classic failure modes any marine-biology pipeline encounters:
      - **Species misidentification** (similar mussel species — `Mytilus edulis` vs `Mytilus galloprovincialis` vs `Mytilus trossulus` look essentially identical externally; field IDs are notoriously wrong without lab confirmation)
      - **Length measurement inconsistencies** (mm vs cm, calipers vs eye-estimate, whether shell length means total or aperture)
      - **Sample-effort inconsistency** (number of hauls, time-per-haul, depth, whether empty hauls were recorded as zeros or omitted entirely — a *missing* zero is much worse than a recorded one)
      - **Coordinate precision drift** (handwritten lat/lon vs GPS; "rough" GPS waypoints; coordinates entered in different formats — DMS vs decimal — and parsed identically)
      - **Date-of-collection vs date-of-entry confusion** (fishermen filling out logs in batches at end of week; the "collection date" column is actually "logged date")
      - **Unit ambiguity in counts** (individual mussels vs cluster counts vs estimated-by-volume)
    - Every one of these produces *plausible-looking values in the right column*. Type checks pass. Schema validators pass. The downstream analysis silently uses wrong assumptions about what each number means.
  - **The handoff dynamic is the load-bearing observation.** The fishermen-to-analyst story is a stand-in for the much larger pattern: **any time data crosses a context boundary** — collector to processor, vendor to consumer, instrument to pipeline, field team to lab team, one institution to another — the *implicit knowledge* that made the data interpretable on the producer side fails to cross with it. The preflight discipline exists to surface that gap **at the boundary** rather than letting it propagate downstream silently. *(Echoes Constance Martineau's "model boundary shape before domain meaning" — same principle generalized to data quality.)*
  - **Why a domain example matters for credibility.** This isn't a hypothetical "imagine a payload" code example like Koudai's PATCH bug. It's a concrete, named scientific-data scenario with real consequences (mussel populations inform fisheries management, conservation decisions, ecological-baseline studies). The cost of "data looks right but isn't" in this domain is *policy decisions made on bad data* — not a 500 error in a web request, but actual ecological / economic consequences. **The stakes raise the talk's argument.**

- **Concrete bad-data catalogue from the slide:** speaker enumerates five canonical failure modes that show up in real museum / fisheries data:
  - **`(0, 0)` coordinates** — the classic "null island" problem. Latitude/longitude defaulting to zero when GPS fails, when fields are left blank and the database inserts zero, or when the import script's `or 0` fallback fires silently. (0°, 0°) is in the Atlantic Ocean off the African coast — biologically nonsensical for almost any terrestrial / freshwater specimen, but *syntactically valid as a coordinate*. **The classic example of "looks right but isn't"** — passes every schema check, fails every domain check.
  - **Taxonomy wrong** — wrong scientific name, misspelled genus / species, synonymized name no longer current, hybrid name format ambiguity (e.g., `Mytilus × galloprovincialis` vs `Mytilus galloprovincialis`). Validating taxonomy requires *reference data* (a current taxonomy database like GBIF, ITIS, World Register of Marine Species); you can't do it from schema alone.
  - **Invalid date format** — unparseable dates (`32-13-2024`), ambiguous formats (`05/06/2024` → May 6 or June 5?), partial dates (`2024-06` with no day), historical dates with calendar uncertainty (Julian vs Gregorian for pre-1752 specimens), futures (date *after* today for a specimen *being* collected).
  - **Duplicate IDs** — primary-key violations. Two records with the same specimen ID. Often happens when curators copy-paste rows, or when two field teams independently assign IDs from the same range.
  - **Missing linked sample** — foreign-key violation. A record references a parent specimen / sample / collection event that doesn't exist in the dataset. Orphaned subrecords are silent until you try to JOIN.
- **The consequence — "broken joins / references."** Each of the catalogue items above eventually manifests as a *failed join* downstream. Duplicate IDs break uniqueness assumptions in any one-to-many join; missing linked samples produce NULL-filled inner-join results or get silently dropped in outer joins; coordinate-zero data clusters in geographic joins and pollutes spatial-analysis results. **The validation issues are the *cause*; broken joins are the *visible symptom*** — usually weeks or months after the data was handed off, when an analyst finally runs the right query.
- **Cost: "curator / repo rejection."** What happens when the dataset is submitted to a downstream repository (GBIF, iDigBio, Symbiota, a journal's data supplement, an institutional collection management system): the curators / automated validators **reject the submission**. The originating team then has to fix the issues *retrospectively* — usually after some weeks of waiting in the queue, having to remember context that's gone stale, often with the original collector unavailable. **The cost asymmetry is the talk's whole point:**
  - **Preflight cost** (catch the issue at handoff): minutes of validator time + maybe an hour to fix the offending records while context is fresh.
  - **Post-rejection cost** (discover the same issue at the repository): weeks of wait, hours of forensic reconstruction, possibly *unfixable* if the field team has dispersed or the season has ended.
  - Ratio is easily 10–100× depending on how cold the trail goes. Same logic as catching a bug in code review vs. catching it after deployment, applied to data.
- **Slide title naming the structural property: *"Hidden issues survive handoff."*** This is the *why* under the bad-data catalogue. The dangerous failures aren't the loud ones (a corrupted file, a parse error, a hard schema violation) — those fail visibly at the moment of transmission and get fixed immediately. The dangerous ones are the *silent survivors*: errors that *plausibly look like valid data* and therefore make it through every gate that does only form-checking.
  - **The combination of "looks right" + "survives handoff" is the talk's complete failure-mode definition.** Either property alone isn't dangerous:
    - Data that doesn't look right but doesn't survive handoff → caught immediately, fixed.
    - Data that looks right but doesn't survive handoff → caught at the receiving end, repository rejects, kicked back.
    - **Data that looks right AND survives handoff → reaches the analyst / publication / model unflagged. This is the failure class preflight is designed to catch.**
  - **Why handoffs are the specific danger zone.** A handoff is the point at which *implicit producer-side context drops out*. The producer (fisherman, curator, instrument operator) had context that made the data interpretable — knowledge of which species are easy to confuse, which GPS regions had reception issues that day, which sample IDs got accidentally re-used. None of that context crosses with the data. So at the handoff moment, **the data goes from "checked against producer context" to "checked only against the bare file's contents"** — and a huge fraction of the producer-side validation evaporates. Preflight is the discipline of *forcing the producer-side checks to be explicit in the file* before the handoff happens. If the producer doesn't encode "coordinates must be non-zero" or "species must be in the WoRMS database" as an explicit assertion, no one downstream can recover the check.
  - **Mental model: the handoff is the point where context becomes inaccessible. Preflight is the discipline of making the implicit context explicit *while it's still accessible*.**
- **The current workflow — what most teams do today (slide diagram):**
  > **"Data doesn't structure itself."** → **Dataset prep** → **Manual or script checks** → **Submission to repo** → **Curator review** → **Resubmit** *(loop on rejection)*
  - **"Data doesn't structure itself"** is the load-bearing opener — *someone or something* has to do the structuring step (transcribing from field forms, exporting from instruments, reshaping spreadsheets, mapping vocabularies). This is **where most errors enter the system**: human transcription mistakes, scripts with brittle assumptions, ad-hoc transformations done years ago by someone who's left, regex-based "cleaning" that silently mangles edge cases. The slide is naming the *origin* of the problem, not just describing it.
  - **The resubmit loop is the cost-multiplier.** Issues caught at curator review send the dataset back to the originating team for fixes — and *each loop* through the cycle costs days-to-weeks (curators have queues; teams have moved on to other work; original context has decayed). The talk's likely thesis: **collapse the resubmit loop by moving the curator-style checks upstream into the "manual or script checks" step.** Same checks, run earlier, before the package is sent.
  - **Where preflight fits in this workflow:** between "dataset prep" and "submission to repo" — augmenting (or replacing) the "manual or script checks" step with a *systematic, repeatable, comprehensive* set of validations. The goal isn't to eliminate curator review (curators catch things automated tools can't), it's to **eliminate the failure modes curators have already named** so the submission succeeds on the first pass.
  - **The implicit comparison the slide sets up:** today's workflow has the *consequences* (curator rejection) acting as the *check* (you find out what's wrong when it gets bounced). Preflight inverts this — *the check exists at the origin*, and the consequences become *signals on the production side*, not the receiving side. Faster feedback, cheaper fixes, less wait-state.
- **What preflight means — the proposed workflow (new slide):**
  > **Validate** → **Review findings** → **Package and share** → **Rerun validation**
  - **Validate** — run an automated suite of checks against the dataset. Catches the catalogue items from earlier (zero coordinates, taxonomy errors, date parsing, duplicate IDs, missing references) automatically. The "you don't need tons of rules" caveat below means this step is *bounded* — not "validate against every possible quality concern," just "validate against the high-frequency known failure modes."
  - **Review findings** — a human (data owner / curator / domain expert) reviews the validator's output. Important that this step exists *and* is separate from validation: automated checks produce *signals*, humans produce *decisions*. The validator can't know whether a flagged record is "really wrong" or "looks wrong but is correct for unusual reasons" (e.g., a specimen genuinely collected near (0,0) on the equator). The human-in-the-loop step is where domain knowledge converts signals into actions.
  - **Package and share** — bundle the validated dataset with its validation results / manifest / metadata, then hand off. **Critical implicit recommendation: the validation result travels *with* the data**, not as a separate artifact that might get lost. The downstream consumer can see exactly what was checked, what passed, what was reviewed-and-accepted-as-edge-case. Trust is *evidenced*, not asserted.
  - **Rerun validation** — at the receiving end, by the downstream consumer / next step in the pipeline, the same (or stricter) validators run again. **This is the "preflight" metaphor's most direct mapping:** a pilot's preflight is run *before takeoff*; here the rerun is done by the next consumer to confirm nothing changed in transit and that their stricter requirements are also satisfied. Detects in-transit corruption, format drift between versions of the validator, and the consumer's domain-specific checks (which the producer may not have run).
- **Key principle for adoption — *"You don't need tons of rules to be useful."***
  - Single biggest objection to adopting preflight is "we'd need to model every possible quality concern before we start." This slide cuts that objection at the root: **start with a small number of high-value rules; ship working improvements immediately.**
  - Echoes the same Pareto pattern across this conference's data-quality theme:
    - Constance Martineau's SWE-vs-DE talk: *"3% of DAGs cause 67% of failures"* — most reliability gain comes from a small set of high-leverage targets.
    - Koudai Aono's Beyond Optional talk: *"Pick one boundary crossing"* as step 1 of the adoption checklist — start narrow, expand later.
    - Jennifer's preflight here: *"You don't need tons of rules"* — same shape applied to data-quality rules.
  - **The cross-talk principle that's clearly emerging:** *small, deliberate, high-leverage starts beat comprehensive-upfront-design.* Three different speakers, three different problem domains, same adoption philosophy. Worth flagging as a meta-takeaway from the whole conference's data track.
  - **Mental model for picking the first rules:** look at the curator-rejection history. Whatever made datasets get bounced in the past *is* the validated-by-the-real-world list of rules you should run as your preflight. You don't need to invent rules — you need to **codify the rules curators have already been enforcing implicitly**, so the team can self-check before submitting. That's a finite, knowable, high-value list.
- **Important property for "package and share": *deterministic outputs.*** Speaker explicitly flags this — running the validator twice on the same dataset must produce the same result, ideally byte-for-byte.
  - **Why this matters non-obviously:** the validation result is itself an artifact that needs to be trustworthy. If running validation locally produces a different report than the producer's report, the consumer can't tell whether (a) the dataset got corrupted in transit, (b) the validator version differs, or (c) the validator is just nondeterministic and the reports were never going to match. **Determinism collapses three classes of confusion into "real differences only."** Without it, every report becomes suspect.
  - **Concrete things this implies the tool does:**
    - **Sorted findings** before serialization — never relying on dict / set iteration order
    - **No timestamps in default output** (or timestamps clearly marked and excludable from diffs) — every run otherwise produces a different file even when the dataset hasn't changed
    - **Fixed random seeds** anywhere sampling is involved — if the validator subsamples for performance, the sample must be reproducible
    - **No machine-specific paths / hostnames / usernames** embedded in reports
    - **Canonical JSON / YAML / CSV output** — same content always yields identical bytes
  - **Why this is a mature-author tell.** Determinism is a non-obvious requirement — most data-quality tools start by emitting "here are the findings" with whatever ordering happened to come out of the dict, plus a timestamp at the top "for convenience." Six months in, users complain that "I can't tell if anything changed" because every report diff is noise. Designing-for-determinism *from the start* means Jennifer's team has been through that pain cycle already and shipped the corrected tool. **The fact that this property gets its own callout on the slide is itself a credibility signal.**
  - **Direct benefits of deterministic outputs:**
    - **Diff-friendly** — store reports in git; reviewers can see what changed between runs at a glance.
    - **CI-friendly** — every commit/PR gets a reproducible validator result; failures aren't flaky.
    - **Verifiable** — a downstream consumer running the same validator on the same data *must* get the same report; mismatches are real signals, not noise.
    - **Reproducible scientific claims** — for academic / regulatory contexts especially, "I ran this validator and got this result" is a falsifiable claim only if the result is deterministic. Otherwise it's not science, it's an anecdote.
  - **Connects to the "rerun validation" step in the workflow:** deterministic outputs are what make the *rerun* step meaningful. If the downstream consumer reruns and gets a different answer, *that* is information — either the data has changed (transit corruption) or the environment has drifted (validator version, dependency resolution). Without determinism, you can't tell signal from noise on the rerun.
- **Per-step requirements — the speaker now annotates each workflow step with its key properties:**

  | Step                  | Required property / capability                                                  |
  |-----------------------|---------------------------------------------------------------------------------|
  | **Validate**          | *Run validation checks: required fields / formats / IDs*                        |
  | **Review findings**   | *Human-readable findings* + *what to fix, why it matters*                       |
  | **Package and share** | *Deterministic outputs*                                                         |
  | **Rerun validation**  | *Verify fixes, track what cleared*                                              |

  - **Validate — "required fields / formats / IDs":** the three workhorse categories the validator must cover. **Required fields** = presence checks (no missing values where the schema demands a value). **Formats** = shape checks (dates parse, coordinates are in range, taxonomy strings match a vocabulary). **IDs** = referential checks (uniqueness, no duplicates, foreign keys actually resolve). These are the bottom-of-the-barrel rules — the *minimum* viable preflight catches all three. Anything below this floor isn't really a preflight; anything above it is iteration on the same primitives.
  - **Review findings — "human-readable findings" + "what to fix, why it matters":** the validator must do more than emit a JSON blob of failures. **Human-readable** = a curator-or-collector should be able to read the report and understand it without having to interpret error codes, JSON paths, or stack traces. **What to fix** = each finding includes *actionable* remediation guidance (which record, which field, what the expected value looks like). **Why it matters** = each finding includes the *consequence* if unfixed — why this is a problem, not just that it's a problem. Without the "why," fixers tend to dismiss findings they don't immediately understand the impact of ("this seems fine, let me just submit it"). The "why" is the load-bearing piece that converts the report from a checklist into a *decision aid*.
  - **Package and share — *deterministic outputs* (detailed above):** covered in the previous block.
  - **Rerun validation — "verify fixes, track what cleared":** the rerun step has two complementary jobs.
    - **Verify fixes** — after the producer addresses findings, the rerun confirms the fixes actually resolved the issues. Catches "thought I fixed it but the fix was wrong" situations cheaply.
    - **Track what cleared** — produces a *delta* report between the previous run and the current one. Findings that disappeared, findings that newly appeared, findings unchanged. This is the *audit trail* that turns the preflight from a one-shot check into a *progress narrative*: "we fixed 47 of the 52 issues from yesterday's run; here are the 5 that remain plus 2 new ones that came in with the additional records."
  - **Combined: the four steps + four properties define a minimum-viable preflight tool spec.** A team building or adopting preflight should be able to walk down this matrix and ask "do we have each of these properties for each step?" Anything missing is a gap to close before the discipline is real. **The matrix is the operational definition of "preflight."**
- **New slide: *"Start small and local."*** Headline message: *"A small number of reusable checks catch many downstream issues."*
  - **Three qualifiers doing distinct argumentative work:**
    - **Small** — a handful of rules, not hundreds. Same Pareto observation as the "you don't need tons of rules" principle earlier, now operationalized as the *adoption* approach. **Adoption is gated on starting small;** teams that try to encode every imaginable rule before they ship anything ship nothing.
    - **Local** — focused on *your* dataset's actual failure patterns, not on a generic kitchen-sink validator that tries to cover every possible quality concern across all possible datasets. The "local" qualifier explicitly opposes "let's adopt the full FAIR-data principles for our institution starting today!" — that's the maximalist trap that derails most data-quality initiatives. Instead: **find the 5 rules your team's data violates most often, ship those, iterate.**
    - **Reusable** — the small set of rules you write should work *across multiple datasets and collections*, not be one-off per file. A check like "coordinates must not be (0,0)" applies to every coordinate-carrying dataset; a check like "row 12 column 3 must equal 'X'" applies to one file. **Reusable rules amortize the writing cost across many uses;** one-off rules don't. Investing in reusable rules creates a *library* that grows over time and becomes more valuable; investing in one-off rules creates a *backlog* that grows over time and becomes more painful.
  - **The "catch many downstream issues" claim is the empirical payoff:** if the rules are small, local, and reusable, the *leverage* is huge — a handful of carefully-chosen rules can prevent a disproportionate share of curator rejections, broken joins, and downstream-analysis failures. This is the same Pareto observation that recurs across every data-quality talk today — Constance's 3%/67%, Koudai's "pick one boundary," Jennifer's "small number of reusable checks." **Three speakers, three problem domains, same lesson:** *most of the value is concentrated in a small number of high-leverage interventions; start there and resist the urge to comprehensively model everything.*
  - **Practical implication for tool adoption:** when introducing preflight on a team, **don't ship the validator with 50 rules.** Ship it with 5. Show the wins. Add rules as new failure patterns emerge or get reported. The library grows organically with real-world signal, not speculatively in advance. This is the same pattern Koudai's adoption checklist uses ("pick one boundary crossing") and Constance's recommendations imply ("know your always-broken DAGs" → triage the 3% before the 97%).
  - **The talk's structural unity across speakers:** between this slide and Koudai's checklist and Constance's empirical findings, today's data-track is *implicitly* arguing for a single methodology — **"minimum viable correctness discipline":** start small, ship working improvements, expand as warranted by real signal. None of the three speakers said this in those words; all three are advocating it in different vocabulary.
- **The actual high-signal check list — the starter set she recommends:**
  - **Duplicate IDs** — primary-key uniqueness. Catches transcription duplication, range-conflict assignment errors.
  - **Suspicious coordinates** — `(0, 0)` and other defaults / sentinels masquerading as locations. Catches GPS-failure-falls-to-zero and form-blank-default-fills.
  - **Invalid ISO dates** — dates that don't parse as ISO 8601, or that are syntactically valid but semantically impossible (Feb 30, future collection dates). Catches the most common date-format failures.
  - **Invalid country codes** — country fields that don't match a controlled vocabulary (ISO 3166-1 alpha-2 or alpha-3). Catches typos, deprecated codes, English-vs-local-language confusion.
  - **Severity levels tagged with each finding.**
  - **Pattern recognition** — this is *exactly* the "small + local + reusable" list the previous slide promised: four rules, each catching a specific high-frequency failure mode, each *reusable* across any dataset carrying coordinates / dates / IDs / country codes. **Together they probably cover 50-80% of curator-rejection reasons** for natural-history-museum data without any per-collection customization. Four rules to ship the first useful version of preflight; iterate from there.
- **Severity levels — the second-order property each finding carries.** Not all findings are equal:
  - **Error / blocker** — *will* be rejected at the repository. Duplicate IDs and missing required fields typically land here. Fix-before-submit is mandatory.
  - **Warning** — unusual and worth a human glance, but not auto-rejected. Suspicious coordinates often fit here (might be legit if the specimen is genuinely from a (0,0)-ish location; *probably* not). The reviewer either accepts the edge case (with documentation) or fixes it.
  - **Info / suggestion** — non-blocking advisories. Often used for nudges like "this date format is technically valid but `YYYY-MM-DD` is preferred" or "this country code is alpha-2; the repository accepts alpha-3 if you prefer." Helpful, not required.
  - **Why severity matters operationally:** it converts the validator output from a flat list into a **triaged action plan**. The producer can mechanically work through *errors first*, batch-decide on *warnings*, and consider *info* items at leisure. Without severity, every finding looks equally urgent (or equally dismissable), and reviewers either drown in unimportant items or skip past genuine errors.
  - **Direct parallel to linters and type checkers** — mypy distinguishes `error`/`note`/`warning`; ruff uses prefix codes (`E`/`W`/`I`/`C`/`N`) with severity baked in; pylint has `E`/`W`/`C`/`R`/`F`. The pattern is well-established in code-quality tooling; Jennifer is naming the data-quality analog. **Treating data validation like code linting** is itself an important conceptual move — same triage discipline, same severity tagging, same iterative tightening of rules over time.
- **Python architecture slide — "Reusable validation workflows built from small components."** The tool is Python-based, with **YAML as the rule-definition DSL**. Slide shows a YAML snippet declaring a rule with regex pattern, modal config, etc.
  - **The architectural choice in one sentence:** *Python engine + YAML rule definitions.* Python handles the execution, IO, error reporting, and composition logic; YAML handles the *what to check* declarations. Rule authors write YAML; library maintainers write Python.
  - **What "small components" probably means** *(without seeing the full slide):*
    - **Atomic check primitives** in Python — regex match, vocabulary lookup, range check, uniqueness check, foreign-key check, presence check, format parse. Each implemented once, exposed as a YAML-addressable type.
    - **Rules compose multiple atomic checks** — a "valid coordinate" rule might combine "is numeric," "in range -90 to 90," "not equal to 0", as a single named check.
    - **Workflows compose rules** — a "fisheries dataset preflight" workflow runs N rules in sequence, aggregates findings, produces a single report.
    - **Composition is the value-add** — primitives alone are cheap, but the gain is in the *reusable rule library* that gets built on top: once "valid coordinate" exists, every dataset with coordinates uses the same rule, fixes propagate everywhere, and new failure modes get added in one place.
  - **Likely shape of a YAML rule** (reconstructed from "regex + modal config"):
    ```yaml
    - name: valid_iso_date
      description: "Collection date must be ISO 8601 (YYYY-MM-DD)"
      field: collection_date
      check:
        type: regex
        pattern: '^\d{4}-\d{2}-\d{2}$'
      severity: error
      mode: strict     # ← "modal config" — could be strict/lenient/skip
      fix_hint: "Reformat as YYYY-MM-DD."
    ```
    - "Modal config" most likely means **per-rule mode** — a rule can be `strict` (fail loudly), `lenient` (warn but allow), or `skip` (disable). Same rule library, different team strictness profiles, no need to maintain multiple rule files. Some teams running the same validator under different mode profiles is exactly the use case YAML-config DSLs are built for.
  - **Why YAML DSL specifically — the tradeoff:**
    - **Pros:** human-editable by non-Python-engineers (curators / domain experts can write rules); version-controllable in git; declarative (the rule says what to check, not how); easy to validate with a meta-schema; portable across tools that consume the same DSL.
    - **Cons:** limited expressiveness — can't run arbitrary code, so anything more complex than the DSL grammar requires either extending the DSL or escape-hatching to Python; YAML's quirks (significant whitespace, type-coercion surprises like `Norway: NO` getting interpreted as boolean false) bite occasionally; debugging is harder than Python (a typo in a regex inside a YAML string gets you a runtime check failure with poor context).
    - **The tradeoff is *right for this domain*** — data-quality rules are mostly simple declarative statements (this field must match pattern X, this field's values must come from vocabulary Y, this combination must not occur). The 20% of cases that need real code are the escape-hatch territory. **Most of the value is in YAML; the escape hatch is rarely used; the abstraction earns its keep.**
  - **Industry precedents this echoes:**
    - **Great Expectations** — YAML expectation suites + Python execution engine. Closest spiritual cousin.
    - **dbt** — YAML `schema.yml` for declarative tests + SQL/Python execution. Different domain but same architecture.
    - **Soda** — SodaCL is a YAML-based data-quality check language.
    - **OpenAPI** — itself a YAML/JSON DSL for API contracts, with Python tools (e.g., Koudai's `datamodel-code-generator`!) consuming it.
    - Jennifer's tool is operating in a well-traveled architectural space — picking a known-working pattern, not inventing new ground. That's a feature, not a limitation: less risk of design dead-ends.
  - **What this architecture choice enables:**
    - **Rule-library reuse across datasets** — once the team has 30 well-tested rules in YAML, applying them to a new collection is a config-change, not a code-change.
    - **Cross-institution sharing** — rule libraries can be published, forked, contributed to. The FAIR-data community has a clear path to share-and-version "what good data looks like" via YAML rule packs.
    - **Mode-based deployment** — same library, strict in production, lenient during development, skip during early data collection. One library, many strictness profiles.
    - **Non-engineer rule authorship** — curators and domain experts can write and review rules without Python knowledge. Lowers the rule-contribution barrier and broadens the contributor pool.
  - **Slide annotation reinforces:** *"small checks, declarative."* Two-word summary of the architectural commitment. *Small* (atomic primitives, not monolithic rules) + *declarative* (state what to check, not how) — together those produce the composability and the cross-team reusability that justify the YAML DSL.
- **The pipeline shape — three artifacts, three audiences:**
  > `rulepack.yml` → `findings.json` → `report.md`
  - **`rulepack.yml`** — declarative input. Authored by humans (curators, domain experts, engineers). Lives in version control. Reviewed via PRs. **Audience: rule authors.**
  - **`findings.json`** — structured machine-readable output of running the rules against a dataset. Stable schema, deterministic, diff-friendly. **Audience: other tools** (CI systems, dashboards, ticket trackers, downstream validators that want to consume the findings programmatically).
  - **`report.md`** — human-readable summary derived from the JSON findings. Markdown for easy rendering in GitHub PRs, docs sites, emails, Slack. Includes the *human-readable findings* / *what to fix, why it matters* properties from the earlier requirements matrix. **Audience: reviewers and producers** — the people who need to act on findings.
  - **The architectural elegance: one canonical structured representation, two materialized views.** The JSON is the *source of truth*; the Markdown is a *rendering*. If you want a different rendering (HTML report, Slack message, ticket-tracker import), you write a new renderer that consumes the same JSON — without touching the rule definitions or the engine. **Decoupling output format from validation logic is what makes the tool extensible without changes to the core.** This is the same architectural pattern as compilers (one AST, many backends) and many static-analysis tools (SARIF as the structured intermediate, with human-readable renderers built on top).
  - **The pipeline also doubles as a *handoff artifact set.*** When the producer hands off a validated dataset, they hand off:
    1. The dataset itself
    2. The `rulepack.yml` that was used to validate it (so the consumer can re-run)
    3. The `findings.json` from the producer's run (so the consumer can verify reproducibility — same data + same rules = same findings)
    4. The `report.md` (so the human consumer can see the validator's narrative without parsing JSON)
    - **All four artifacts together = the "validation result travels with the data"** principle made concrete. The package-and-share step is well-defined: ship the 4 artifacts as a bundle.
- **Next slide preview: *"structured findings"*** — about to detail the `findings.json` schema specifically. Expect the shape to include things like:
  - Finding ID (stable identifier — useful for the "track what cleared" rerun step)
  - Rule name / reference back to the rulepack
  - Severity (error/warning/info)
  - Location pointer (file, row, column, field)
  - Observed value vs expected value
  - Fix hint
  - Possibly a JSON Pointer / JSON Path locator into the original dataset
  - Probably aligns with a known standard like **SARIF** (Static Analysis Results Interchange Format) or its data-quality cousin — would be a natural choice for cross-tool interoperability.
- **The structured-findings dataclass — actual on-slide code:**
  ```python
  @dataclass
  class Finding:
      code: str           # rule identifier (e.g., "DUP_ID", "INVALID_DATE")
      severity: str       # "error" / "warning" / "info"
      where: str          # location pointer — file/row/column/field path
      why: str            # explanation of why this matters
      how_to_fix: str     # remediation guidance
      details: dict       # rule-specific context (observed value, threshold, etc.)
  ```
  - **Five required string fields + one details dict.** The shape is *opinionated about explainability* — `why` and `how_to_fix` are **first-class typed fields**, not optional metadata, not "TODO add docs later." Every finding the tool produces is *required* to include both. This directly encodes the "what to fix, why it matters" requirement from the earlier matrix into the *type system*. **The dataclass makes it impossible to ship a finding without the explainability fields.** That's a load-bearing design choice.
  - **Field-by-field, what each is doing:**
    - **`code`** — the rule's stable identifier. Same role as `E501` in flake8 or `RUF001` in ruff. **Stable across runs** — used by the rerun step to track which findings cleared. Also the natural primary key for cross-referencing into documentation, ignore-lists, suppression configs.
    - **`severity`** — triage level. Drives the "fix in this order" workflow.
    - **`where`** — locator into the dataset. Could be a file path, a row index, a CSV column, a JSON Pointer, etc. The string form is flexible; the tradeoff is that consumers need to know how to parse the locator string. (A more structured form would split this into separate `file`/`row`/`column` fields — flexible vs strict tradeoff; she chose flexible.)
    - **`why`** — domain-meaning explanation. Not "the regex didn't match," but "this date format can't be sorted chronologically by downstream tools, which will produce wrong timelines in the analysis." The *consequence*, not the *mechanic*.
    - **`how_to_fix`** — actionable remediation. Specific to *this* finding, not a generic doc-link. "Change `06/15/2024` to `2024-06-15`" beats "use ISO 8601 dates."
    - **`details: dict`** — escape hatch for rule-specific context. The observed value, the expected value, the threshold, the vocabulary that was checked against. Anything that doesn't fit one of the five typed slots goes here, structured but unschema'd. **Right tradeoff between consistency and extensibility:** the typed fields are stable contract; details flexes per rule.
  - **Why this beats a free-form JSON schema:**
    - **The dataclass *is* the schema.** Python tools that consume findings (the report renderer, the rerun-delta engine, custom dashboards) all import this class and get type-checking + IDE autocompletion for free. No separate JSON-Schema file to keep in sync.
    - **`asdict(finding)` gives JSON-ready output.** Determinism is easier to achieve (consistent field ordering from the dataclass definition), serialization is built-in, no manual `to_dict()` method.
    - **Equality, hashing, and comparison work by default.** Two findings with identical content are `==`-equal — useful for deduplication and the "what cleared" diff in the rerun step.
    - **Tooling can extend via subclassing** — `@dataclass class ExtendedFinding(Finding)` with extra fields, for tools that need more context. The core schema stays stable; specializations stack on top.
  - **The `Finding` dataclass is the bridge between the YAML rule (declarative description of *what* to check) and the structured output (machine-readable record of *what failed*).** Rules emit Findings. Findings serialize to JSON. JSON renders to Markdown. **Single internal type, well-typed, semantically rich, drives the whole downstream pipeline.** This is the *load-bearing data structure* of the whole tool — and it's a 6-field dataclass.
  - **Speaker's justification: *"structured findings scale better than giant transaction logs."***
    - Direct comparison: many data-quality tools today produce a *log* of everything they checked (and sometimes everything that passed). The output is a wall of text — useful for debugging a single dataset, useless at scale when you need to aggregate across runs, datasets, teams.
    - **Structured findings let you ask questions log dumps can't easily answer:** "across our last 30 collections, how many `INVALID_DATE` findings did we get?" "Which `code` shows up most often?" "Which datasets had zero findings vs ≥10?" "Which findings cleared between yesterday's run and today's?" Each of these is a one-liner against a list of `Finding` dataclasses (or one SQL query against the JSON exports). With logs, each is a grep-and-awk safari.
    - Same argument as **structured logging vs print-debugging** in app dev. When you have N events, the structure pays for itself: you can group, filter, count, diff. The unstructured-log approach works at small N and falls apart as N grows. Jennifer is naming the data-quality version of that lesson.
    - **The scale argument matters specifically for *organizational* preflight adoption**, not just one-off use. A solo curator checking one dataset might get by with log output; a team running preflight on every submission to a shared repository needs the aggregate view. Structured findings are the *foundation that the aggregate view is built on top of.* You can't retrofit structure onto unstructured logs.
- **Next slide preview: *"human-readable reports."*** About to detail the `report.md` rendering step — how the structured findings get converted into human-readable Markdown for reviewers. Expect: summary stats at the top (counts by severity), grouped findings by code or by location, the `why` and `how_to_fix` fields prominently displayed per finding, possibly a "what cleared since last run" delta section.
- **Human-readable reports slide — properties:**
  - **Generates human-readable Markdown** — the format itself is chosen for both *human readability* (renders nicely in any Markdown viewer) and *machine accessibility* (still text, still diffable, still committable to git).
  - **Grouped findings** — organized by code / severity / location rather than presented as a flat list. Grouping makes a 200-finding report tractable; a flat list of 200 findings is just a wall of text. **Same set of findings, different presentation, dramatically different usability** for the reviewer triaging them.
  - **Row-level references** — each finding points to a specific row (and ideally column / field) in the source data. The reviewer can read a finding and immediately open the dataset to that row, see the bad value in its actual context. **Locating the problem is the bottleneck in fix-cycle time;** baking the reference into the report collapses it to one click.
  - **Deterministic reruns** — re-rendering the report from the same JSON findings produces byte-identical Markdown. Same property as deterministic JSON output, applied to the next layer. **This lets reports themselves be diff-friendly artifacts** in git, so PRs that fix data issues show *exactly which findings cleared* as a diff of the report.
  - **Actionable outputs** — the `how_to_fix` field gets prominent display per finding, not buried in a details section. The report reads as a *task list*, not a list of complaints. Reviewers can work through it linearly and act on each item.
  - **All four properties point at the same underlying philosophy: the report is a *workflow artifact*, not a status dump.** It exists to *drive action*, not to inform passively. Grouping makes findings tractable; row references make fixes locatable; determinism makes progress measurable; actionable hints make next steps obvious. Without all four, the report falls back into "wall of text the team learns to ignore."
- **New slide: *"Reruns highlight what changed."*** The rerun step isn't just "do it again" — it produces a **delta view** comparing the current run against the previous one. Three categories of findings get distinct treatment:
  - **Cleared** — was in previous run, gone now. Marked as resolved. **The morale-boost category** — visible proof that fixes worked.
  - **Persistent** — was in previous run, still here. Marked neutral. Carry forward; keep working through them.
  - **New** — wasn't in previous run, appeared now. Marked as regression / newly-exposed. **The danger category** — either you accidentally broke something while fixing, or new data was added that exposed previously-hidden issues. **New findings deserve the loudest attention** because they represent fresh signal, not stale-residue.
  - **Why this is the operationalization of "track what cleared" from the requirements matrix:** the rerun without the delta is just another flat report — useful as a snapshot but not as a *progress narrative*. The delta is what turns the rerun from a verification step into a **continuous improvement loop**: each run shows the team how far they've come and what's left.
  - **Direct enabling property: determinism.** Without deterministic outputs (validate step) and deterministic JSON (package step) and deterministic Markdown (report step), the diff would be flooded with non-meaningful changes — re-ordered findings, timestamp drift, irrelevant whitespace. Determinism throughout the pipeline is what makes the delta *only show real changes*. **The earlier determinism callout pays off here — it isn't a nice-to-have; the rerun-delta feature depends on it.**
  - **Analogous patterns in adjacent tools:**
    - `git diff` — same shape: previous state, current state, highlight what changed.
    - `mypy --baseline` / `mypy-baseline` — baseline file of known issues, new run reports only new findings.
    - `ruff` regression mode — compare new lint output against baseline.
    - CI test result diffs (e.g., GitHub Actions reporting "+3 -7 tests" between commits).
    - All variations on the same core idea: **structured-state + structured-state + diff = progress narrative.** Jennifer's preflight tool inherits this pattern from the wider quality-tooling ecosystem and applies it to data validation.
  - **Bonus organizational effect:** a delta-based report is *easier to motivate work against* than a flat one. "Fix these 30 findings before submitting" is a daunting checklist; "you cleared 47 since yesterday, 5 remain, plus 2 newly appeared with the latest records" is a tractable next-step list with visible momentum. **The format itself shapes whether the team perceives progress.** Worth flagging for any team doing data-quality adoption — the *display* of progress is part of what makes the discipline stick.
  - **Speaker's punchline restating the value prop:** *"Validation becomes more useful when reruns clearly show what improved."*
    - One-line summary of why the delta-tracking discipline is load-bearing, not nice-to-have. Reframes validation from a *gate* ("did this pass?") to a *meter* ("how much better is it now than last time?"). Same activity, different mental model — and the meter is the framing that produces sustained engagement. Gates get gamed or ignored; meters get watched.
    - Connects to the talk's larger arc: preflight is *not* about establishing a perfect-data ideal that gets enforced once. It's about establishing an **iterative improvement discipline** where each rerun is a small, visible step forward. The "small and local + reusable" rule philosophy + delta-tracking reruns + actionable reports together form the loop that makes the discipline self-reinforcing.

- **Closing slide — three takeaways:**
  1. **Start small and local.**
  2. **Make validation reusable.**
  3. **Optimize for humans.**
  - **#1 — Start small and local.** Recapitulates the adoption philosophy: ship 5 high-leverage rules first, expand only as real signal accumulates. Resist the temptation to model everything before launching. **The minimum viable preflight is better than the nonexistent comprehensive one.** Matches the "you don't need tons of rules to be useful" framing from earlier in the talk.
  - **#2 — Make validation reusable.** The YAML rule-pack architecture made tangible: write a rule *once*, apply it across N datasets / collections / institutions. **Investment in reusable infrastructure beats one-off scripts**, because the rule library accrues value over time while one-off scripts accrue maintenance debt. This is the design choice that makes the *first* rule worth writing — if you knew it would never be used again, you'd skip it; the reusability promise is what makes the investment rational.
  - **#3 — Optimize for humans.** The collective theme behind: human-readable findings, `why` and `how_to_fix` as first-class fields, deterministic outputs, grouped + row-referenced reports, delta-tracking reruns. **Every output the tool produces is shaped by the reviewer's needs**, not the engineer's convenience. The `Finding` dataclass with required explainability fields is the most concrete embodiment of this — you literally cannot ship a finding without thinking through what a human would need to act on it.
  - **The three together form a coherent design philosophy:** start small (don't over-engineer up front), build for reuse (so investment compounds), keep humans first (because adoption depends on whether reviewers can actually use the output). **A team that lives by these three principles will produce a usable preflight discipline; a team that violates any of them will produce shelfware.**
