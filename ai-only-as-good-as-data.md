- **"Data agent" defined *(per Ben Pyrt/Park, whoever that is)*: an expert on queries over esoteric databases.** Note this is *one person's framing*, not a universal definition — "data agent" is used differently by LlamaIndex, by Mode (Ben Stancil), by the Anthropic agent docs, etc. Treat as one slice. Specific use case being scoped:
  - **Esoteric** = niche / specialized / domain-heavy. Implied target: databases a general LLM wouldn't know how to query — odd schemas, custom query DSLs, deep domain context.
  - Concrete examples this would cover: scientific repositories (GBIF, NCBI GEO, ENCODE), domain-specific schemas (medical, legal, financial, regulatory), specialized query languages (Cypher / SPARQL / GraphQL / custom DSLs over weird stores).
  - **The value-add of the agent:** encode the domain knowledge — schema, query patterns, common pitfalls, business semantics — so the LLM can navigate data sources it wouldn't handle off-the-shelf. Echoes the same boundary-knowledge problem as Jenny's preflight talk: the *expertise that doesn't travel with the data* needs to be explicitly represented somewhere. **Preflight encodes it as validation rules; data agents encode it as agent context / prompts / skills.** Same problem class, different intervention point.
- **Heavy discussion of: token saving via skills + prompt caching.**
  - **Skills** (Claude Code primitive): reusable prompt-template / system-instruction units loaded on-demand. Don't bake all your domain context into every conversation; load the relevant skill when the task calls for it.
  - **Prompt caching** (Anthropic API feature): mark a static prefix of your prompt as cached. Cache hits cost ~10% of normal input-token price (default ephemeral TTL; 1h available). Massive cost savings for repeated context like system prompts, large reference docs, agent skill content.
  - **Combined play:** put domain context in skills; cache the skill content. Domain expertise gets amortized across many queries at a fraction of the per-call cost. The skill-cache pattern is the cost engineering trick that makes data agents economically viable when you have lots of domain context to inject.
- **Argument for model-agnostic design to save money.** Don't lock your agent stack to one provider; route between models based on cost / capability / latency trade-offs. Common patterns:
  - Cheap model for routing / classification → expensive model for heavy reasoning.
  - Local / open-weight model for high-volume simple tasks → frontier model for hard cases.
  - Same prompt shape across providers (using e.g., LiteLLM, OpenRouter, or your own thin abstraction layer) so you can swap when prices change or new releases ship.
  - **The money argument is the practical one** — frontier-model bills add up fast, and the cost of a model-agnostic abstraction is a one-time engineering effort that compounds in savings forever. Worth flagging that the *implementation cost* of model-agnostic architecture is non-trivial (different providers have different tool-calling conventions, streaming protocols, context limits, caching primitives — abstractions leak).
- **Andy Port:** *"use subagents more."* (Another round-table participant — likely distinct from earlier "Ben Pyrt/Park.")
  - Subagent pattern: decompose a complex agent task into smaller specialist agents, each with narrower scope, focused tools, simpler prompt. Orchestrator dispatches; subagents do the focused work and return.
  - Why "more": smaller scope → better per-agent performance, easier to debug, independent prompt-caching per subagent, can route different subagents to different (cheaper or local) models, parallel execution of independent subtasks.
  - Common in Claude Code (Task tool / subagents), LangGraph, AutoGen, CrewAI. Andy's advocacy is consistent with the broader round-table theme: **agent architecture beats agent intelligence** — careful decomposition + cheap models + caching wins over one expensive monolithic agent doing everything in a single context window.
  - **Your skepticism: "for token saving? can't be helpful."** Actually well-founded. Honest read:
    - **Subagents do *not* inherently save tokens.** Each subagent invocation has its *own* system prompt, tool definitions, context setup — that's *added* overhead, not saved. Orchestrator ↔ subagent round-trips duplicate context. Total tokens across an N-subagent run typically *exceeds* a single big-agent run.
    - **What subagents *do* save:** latency (parallelism), quality (focused prompts → less context confusion), debuggability (smaller scopes), and **cost** (different thing from tokens) when you route subagents to *cheaper* models.
    - **Token savings only materialize indirectly** via: (a) cheaper-model routing, (b) effective caching of *per-subagent* static context, (c) avoiding the catastrophic-context-blowup regime where a single agent's context grows so big that quality degrades and the agent loops / retries — at which point splitting reduces *waste*.
    - **The argument as stated ("use subagents to save tokens") is sloppy.** The defensible version is "use subagents to save *cost*, even though total tokens may go up." Token count and dollar cost are different metrics; conflating them is a common round-table-AI hand-wave.
- **Topic drift: vectorization / RAG / DocumentDB / linking knowledge to data chunks efficiently.** The bulk of the round-table is now in standard RAG territory. Recurring threads in this area:
  - **Chunking strategies** — fixed-size vs. sentence-aware vs. semantic vs. hierarchical. The dimension that most affects retrieval quality.
  - **Embedding model choice** — OpenAI's `text-embedding-3-*`, Cohere, Voyage, open-weight options (`bge`, `e5`, `nomic-embed`). Different cost / quality / dimensionality tradeoffs.
  - **Vector storage layer** — pgvector (Postgres), Pinecone, Weaviate, Qdrant, LanceDB, **DocumentDB** as a Mongo-API-shaped option. The DocumentDB pitch here is presumably "you don't need a specialized vector DB — Postgres-or-DocumentDB can do this with the right extensions."
  - **Hybrid search** — vector + keyword (BM25) + filters. Pure vector retrieval misses exact-match cases; pure keyword misses semantic ones. Hybrid is usually best.
  - **Reranking** — cheap initial retrieval (top-100), expensive rerank step (top-10). Cohere Rerank, custom cross-encoders.
  - **Knowledge-graph supplements** — when relationships matter (not just similarity). Often combined with vector retrieval rather than replacing it.
  - **"Efficient" usually means** — index speed, query latency, cost-per-vector, recall at top-k. Tradeoffs across all these; no universal best.
  - Not capturing in deeper detail since the round-table doesn't appear to be landing novel insights — standard RAG conversation that's been had at every AI/data event for 18+ months.

Browser agents extend that into natural-language-driven flows. **The data-agent vision blurs into the browser-agent vision when the data lives behind a web UI rather than a queryable API.**
- **"Use agents to bounce ideas off other agents."** *(One-off tidbit from a participant — not a central round-table thread, but worth a quick capture.)* Multi-agent peer-review pattern. Standard shape:
  - Agent A generates an answer; Agent B reviews / critiques / debates it; optionally an arbitrator agent resolves disputes. Iterate until convergence or threshold.
  - Implementations across the ecosystem: AutoGen (Microsoft, explicitly built for this), CrewAI (role-based agent teams), LangGraph multi-agent flows, Anthropic's own multi-agent research / critique loops.
  - **Plausible benefit:** different agents catch different errors via diversity-of-prompt-or-model. Critique-and-revise tends to improve over single-shot for hard reasoning tasks.
  - **Honest caveat:** the cost is real. Multi-agent debate often **2-5× the token cost** for marginal quality improvements that depend heavily on the task. Empirically less impressive than the marketing — many "agent debate" papers show modest gains, and a smarter single-agent prompt (chain-of-thought, self-critique inline) frequently matches the cost-adjusted result.
  - **Pattern is real and useful when calibrated**; reflexive "always use multi-agent debate" is the same hand-wave as "always use subagents to save tokens" — sounds sophisticated, doesn't always pay off. Worth doing the cost/quality measurement on your actual task before committing the architecture.
